# Keryx Minimal Daemon RPC/Status Surface Plan

> **For Hermes:** This is a planning-only architecture handoff. Do not implement task execution, relay/A2A integration, or agent lifecycle in this slice.

**Goal:** Define the first minimal Keryx daemon service surface for readiness, status, and doctor behavior, including CLI daemon-client behavior.

**Architecture:** Keep `keryx-core` pure and place runtime/service ownership in `keryx-daemon`. Expose a narrow tonic/protobuf control-plane surface from `keryxd`, with `keryx` CLI either querying a configured daemon endpoint or falling back to local runtime readiness checks. Treat task/agent RPCs in the current proto as future placeholders only.

**Tech Stack:** Rust workspace, `tonic`/protobuf generated by `keryx-proto`, Tokio TCP listener, SQLite-backed `keryx-store` readiness, Clap CLI.

## 2. Minimal service contract

### Boundary

This service surface answers only:

1. Is the daemon/runtime ready enough to be considered alive?
2. What persisted runtime state was used to decide readiness?
3. Which local checks pass/fail for operator troubleshooting?

It must not accept tasks, schedule tasks, register agents, publish relay presence, or subscribe to real event streams in this phase.

### Transport

Use tonic/protobuf over local TCP, consistent with ADR 0002 and current repo code.

- Daemon bind env var: `HERMES_KERYX_DAEMON_ADDR`, for example `127.0.0.1:50051`.
- CLI client env var: `HERMES_KERYX_DAEMON_ENDPOINT`, for example `http://127.0.0.1:50051`.
- Do not add Unix-domain sockets in this slice unless a later explicit task chooses it. TCP is already implemented and testable with tonic without extra transport feature work.

### RPCs

Keep the initial RPCs in `KeryxDaemon`:

```proto
rpc Status(StatusRequest) returns (StatusResponse);
rpc Doctor(DoctorRequest) returns (DoctorResponse);
```

All other `KeryxDaemon` RPCs should remain server-side `Status::unimplemented(...)` with messages that explicitly identify them as outside the readiness slice.

### Request shapes

Keep requests empty for the minimal phase:

```proto
message StatusRequest {}
message DoctorRequest {}
```

Rationale: this phase has no tenant, node, auth, selector, task, agent, or relay inputs. Empty requests make the contract stable and avoid prematurely designing execution semantics.

### Response shape, minimal compatible contract

Current proto shape is acceptable for the first implementation:

```proto
message StatusResponse {
  string status = 1; // "ready" or "not-ready"
}

message DoctorResponse {
  string status = 1;          // "pass" or "fail"
  repeated string messages = 2; // human-readable check lines
}
```

Normative meanings:

- `StatusResponse.status == "ready"`
  - Daemon runtime completed startup.
  - Data directory exists.
  - SQLite store opened and migrations completed.
  - Schema version is readable and greater than zero.
  - Startup recovery completed without error.
- `StatusResponse.status == "not-ready"`
  - Reserved for future partial-startup states. Current implementation should fail startup instead of serving if SQLite/migration/recovery fails.
- `DoctorResponse.status == "pass"`
  - All checks report ready.
- `DoctorResponse.status == "fail"`
  - One or more checks failed.
- `DoctorResponse.messages`
  - Human-readable lines in the existing CLI style, e.g. `[ok] sqlite_store - kind=sqlite path=... schema_version=1`.
  - Messages should be stable enough for smoke assertions but not treated as a long-term machine API.

### Internal report shape

Keep richer structured state internal to `keryx-daemon` rather than forcing it into protobuf prematurely:

- `KeryxStatusReport`
  - `daemon_ready: bool`
  - `data_dir: PathBuf`
  - `db_path: PathBuf`
  - `schema_version: i64`
  - `recovered_tasks: usize`
  - `store: StoreReadinessReport`
- `KeryxDoctorReport`
  - `healthy: bool`
  - `status: KeryxStatusReport`
  - `checks: Vec<DoctorCheck>`
- `DoctorCheck`
  - `name: &'static str`
  - `ready: bool`
  - `detail: String`

Rationale: CLI local fallback can show richer detail without expanding the external proto before the team knows which fields must be stable for SDK consumers.

### CLI contract

`keryx status`:

- If `HERMES_KERYX_DAEMON_ENDPOINT` is a non-empty string:
  - Connect using `KeryxDaemonClient::connect(endpoint)`.
  - Call `Status(StatusRequest {})`.
  - Print:
    - `keryx status: <ready|not-ready>`
    - `source: daemon <endpoint>`
- Else:
  - Start/open local runtime with data dir from `HERMES_KERYX_DATA_DIR` or `.keryx`.
  - Print local runtime status, including data dir, db path, store readiness, schema version, and recovered task count.

`keryx doctor`:

- If `HERMES_KERYX_DAEMON_ENDPOINT` is a non-empty string:
  - Connect using `KeryxDaemonClient::connect(endpoint)`.
  - Call `Doctor(DoctorRequest {})`.
  - Print:
    - `keryx doctor: <pass|fail>`
    - `source: daemon <endpoint>`
    - Each returned message line.
- Else:
  - Start/open local runtime and print local doctor checks.

Exit behavior:

- Successful ready/pass responses exit 0.
- Connection failures, invalid endpoint errors, startup failures, migration errors, or other tonic errors may propagate as non-zero `anyhow` errors for this phase.
- Do not add retry loops, daemon auto-start, background management, or JSON output in this slice.

## 3. Test-first implementation slices

The implementer should proceed in small, test-first slices. Some pieces appear already present; if so, keep the tests and use this as the acceptance checklist rather than rewriting working code.

### Slice 1: Runtime readiness report

**Objective:** Ensure `KeryxDaemonRuntime::startup` exposes a structured readiness report after SQLite startup and lease recovery.

**Files:**

- Modify/test: `crates/keryx-daemon/src/lib.rs`
- Test: `crates/keryx-daemon/tests/startup_recovery.rs`

**Test first:**

- Add/keep test `runtime_status_report_reflects_ready_sqlite_store` asserting:
  - `daemon_ready == true`
  - `data_dir` equals configured data dir
  - `db_path` equals `<data_dir>/keryx.db`
  - `schema_version == 1`
  - `recovered_tasks == 0` for a fresh runtime
  - `store.kind == "sqlite"`
  - `store.ready == true`

**Implementation:**

- Keep report structs in `keryx-daemon`, not `keryx-core`.
- Build the report from `StartupReport` and `KeryxDaemonConfig`.
- Do not add network or filesystem dependencies to `keryx-core`.

**Focused validation:**

```bash
cargo test -p keryx-daemon --test startup_recovery runtime_status_report_reflects_ready_sqlite_store
```

### Slice 2: Runtime doctor report

**Objective:** Provide operator-facing checks derived from the runtime report.

**Files:**

- Modify/test: `crates/keryx-daemon/src/lib.rs`
- Test: `crates/keryx-daemon/tests/startup_recovery.rs`

**Test first:**

- Add/keep test `runtime_doctor_report_marks_runtime_healthy_when_store_ready` asserting checks include:
  - `data_dir`
  - `sqlite_store`
  - `startup_recovery`
- Assert `healthy == true` when all checks are ready.

**Implementation:**

- Add `DoctorCheck` and `KeryxDoctorReport` in `keryx-daemon`.
- Derive `healthy` from `status.daemon_ready && all(check.ready)`.
- Keep check details human-readable and non-secret.

**Focused validation:**

```bash
cargo test -p keryx-daemon --test startup_recovery runtime_doctor_report_marks_runtime_healthy_when_store_ready
```

### Slice 3: Protobuf readiness RPCs

**Objective:** Ensure generated proto includes the minimal readiness service methods.

**Files:**

- Modify, only if missing or mismatched: `proto/hermes/keryx/v1/daemon.proto`
- Usually no change: `crates/keryx-proto/build.rs`
- Test: `crates/keryx-proto/src/lib.rs` or a new focused generated-type test if needed

**Test first:**

- Existing compile is the main test because tonic generated clients/servers fail to compile if methods/messages are absent.
- If adding an explicit generated-type test, assert `StatusResponse { status: "ready".into() }` and `DoctorResponse { status: "pass".into(), messages: vec![] }` can be constructed.

**Implementation:**

- Keep `StatusRequest`, `StatusResponse`, `DoctorRequest`, and `DoctorResponse` in `daemon.proto`.
- Do not expand task/agent messages in this slice.

**Focused validation:**

```bash

```

### Slice 4: Daemon RPC server implementation

**Objective:** Serve only `Status` and `Doctor` over tonic; leave future RPCs explicitly unimplemented.

**Files:**

- Modify: `crates/keryx-daemon/src/lib.rs`
- Test: `crates/keryx-daemon/tests/rpc_status.rs`
- Dependency check: `crates/keryx-daemon/Cargo.toml`

**Test first:**

- Add/keep integration test `daemon_rpc_reports_runtime_status_and_doctor_readiness`:
  - Create temp data dir.
  - Start `KeryxDaemonRuntime`.
  - Bind `TcpListener` on `127.0.0.1:0`.
  - Spawn `serve_daemon_rpc(runtime, TcpListenerStream::new(listener))`.
  - Connect with `KeryxDaemonClient::connect(format!("http://{addr}"))`.
  - Assert `StatusResponse.status == "ready"`.
  - Assert `DoctorResponse.status == "pass"` and messages include `sqlite_store` and `schema_version=1`.
  - Abort server at end.

**Implementation:**

- Add `KeryxDaemonRpcService` wrapping `Arc<KeryxDaemonRuntime>`.
- Implement `keryx_proto::v1::keryx_daemon_server::KeryxDaemon`.
- `status` maps `runtime.status_report().daemon_ready` to `ready`/`not-ready`.
- `doctor` maps `runtime.doctor_report().healthy` to `pass`/`fail` and formats check messages.
- `RegisterAgent`, `DispatchTask`, `GetTask`, and `SubscribeEvents` return tonic `Status::unimplemented` with clear readiness-slice messages.

**Focused validation:**

```bash

```

## 6. Ambiguities, blockers, and risk notes

### Current state observation

The current workspace already appears to contain most of this minimal surface: daemon proto methods, runtime status/doctor reports, tonic service, CLI daemon endpoint path, and focused integration tests. Treat the plan as a formal acceptance checklist and handoff rather than a request to duplicate or broaden the implementation.

### Ambiguities

- Whether the external proto should stay string-only or be upgraded now to structured fields such as `schema_version`, `db_path`, `checks { name, ready, detail }`.
  - Recommendation: keep string-only for this first slice; internal Rust reports already preserve structure and avoid premature public API commitment.
- Whether local transport should eventually be Unix-domain sockets.
  - Recommendation: defer. TCP is already consistent with tonic tests and sufficient for this phase.
- Whether CLI local fallback should mutate by creating `.keryx/keryx.db` when no daemon endpoint is configured.
  - Current behavior does create/open local runtime state. This is acceptable for early readiness checks but should be documented if operator expectations change.

### Risks

- `DoctorResponse.messages` is human-readable, not a stable machine contract. If SDKs need structured diagnostics, add a later proto revision with typed checks.
- `keryxd` currently serves only when `HERMES_KERYX_DAEMON_ADDR` is set. This avoids premature daemonization but can surprise users expecting a default listener.
- Startup failures currently prevent serving rather than returning `not-ready`. This is simpler and safer for the minimal phase, but future supervisor integrations may want a degraded health endpoint.
- Existing task/agent RPC names in `daemon.proto` may imply more functionality than exists. Server-side `unimplemented` responses must remain explicit until those slices are designed.
